# P23.1 — server-side quiz runs, time limits, the review and the quiz lock (backend)

Owner request (12 Nov 2026): the quiz state was not saved (coming back let the intern start over while the admin
had recorded an answer), the intern should not leave a quiz half done, the admin can give a quiz a time limit, the
intern sees a report at the end, and (added later) the assistant cannot be used to look answers up during a quiz.

- **Runs** (`app/quiz_runs.py`, `quiz_runs` table): `POST /api/quiz-runs` starts the profile's run of a set or resumes
  its open one (same items, order, answers, remaining time, on any device; one open run per profile and set, also
  under concurrent starts). A new run puts the questions missed in the intern's last closed run first.
  `POST /api/quiz-runs/{id}/answer` stores one locked-in answer per item (no correctness in the response);
  `POST /api/quiz-runs/{id}/finish` (idempotent) and `GET /api/quiz-runs/{id}/review` return the review (the
  intern's own result, the correct options and the cited rows verbatim). Routes are scoped to the run's profile or
  another profile of the same intern (else 404); an anonymous profile may take only the official quiz.
- **Time limits**: `time_limit_minutes` (1–120 or null) on the admin set create/patch/list; the official quiz never
  has one. The deadline is fixed at start; the server clock decides with a 2 s grace; expiry is lazy (start, answer,
  finish, review, the quiz list, the chat lock and the admin's checkpoint views all notice it).
- **Checkpoint = the first run** (D-P20-checkpoint refined): the admin results, intern detail, final report and the
  intern's `my_result` count the intern's first run (unanswered = not right; later runs never change it). Interns
  with answers from before runs existed keep the earliest-answer rule.
- **Old clients**: `POST /api/quiz/check` still works for the official quiz and untimed practice sets; for an item of a
  timed or checkpoint set it is 400 `field: "id"`, `reason:use_run`.
- **Plan**: finishing a run of the official quiz ticks the plan's quiz activity on the server.
- **Quiz lock** (owner addition): a run of a checkpoint or timed set is `locked` (`QuizRun.locked`,
  `QuizSetSummary.locked`). While the intern has one open and not expired, `POST /api/chat` answers only the fixed
  lock text with `quiz_lock {run_id, set_id, remaining_seconds}` before any guard, retrieval, model call or turn log,
  and `POST /api/check` (new optional `profile_id`) is 400 `field: "profile_id"`, `reason:quiz_open`.
- **Contract** (§6o of `docs/api_contract.md`): new shapes `QuizRunStart`, `QuizRun`, `QuizRunAnswer`,
  `QuizRunAnswered`, `QuizRunFinish`, `QuizRunReview(Item)`, `QuizLock`; `QuizSetSummary` gains `time_limit_minutes`,
  `open_run_id`, `open_run_remaining_seconds`, `last_review_run_id`, `locked`; `ChatResponse.quiz_lock` (left out when
  null); `CheckRequest.profile_id`; error reasons `expired`, `finished`, `answered`, `in_progress`, `use_run`,
  `quiz_open` (frozen enum: 400 `validation_error`). Web: types, guards and `startQuizRun`, `answerQuizRun`,
  `finishQuizRun`, `getQuizRunReview` in `web/src/api/client.ts`.
- **Stores**: migration `supabase/migrations/0011_quiz_runs.sql` (idempotent; RLS on, no policies, revoked); the
  LocalStore creates the same table and upgrades an existing SQLite file (`quiz_sets.time_limit_minutes`,
  `quiz_attempts.run_id`, the partial unique indexes); the SupabaseStore never flips to local for the run tables.
- **Privacy**: `docs/privacy_ai_note.md` §4 table rows and §10.
